# Pulso — Independent Review

*Reviewed: README.md, coach/PROFILE.md, coach/CLAUDE_PROJECT_INSTRUCTIONS.md, coach/SETUP_GUIDE.md, webapp/pulso-panel.html, and coach/Pulso-Macro-Tracker.xlsx (opened with openpyxl, all sheets and formulas inspected). ~20 real days logged as of this review.*

## Overall verdict

Pulso is a well-thought-through *prompt design* (the coaching philosophy, the tone rules, the panel's information hierarchy) wrapped around a data architecture that doesn't actually hold up under its own stated growth path. The panel looks like a small dynamic app but is almost entirely hand-authored prose regenerated from scratch each turn, with only the day-picker's macro bars genuinely data-driven; the spreadsheet looks like a self-maintaining "database" but has a leftover placeholder row silently polluting its first week of averages and two governance tables (the ones specifically built to catch stale data) that are hardcoded to stop working after about 30 rows — a limit the log is already approaching. None of this is catastrophic for a single-user personal tool, and the core coaching logic (protein/fiber as floors, calories/carbs/fat as budgets) is sound. But the system's actual failure mode isn't a crash — it's confidently displaying a wrong number with no signal that anything broke, which is a genuinely bad failure mode for something a 61-year-old is using to make daily eating and training decisions off an ApoB flag. Below are the specific findings, several of which are live bugs, not hypotheticals.

---

## 1. Data architecture

**xlsx as database + hand-copied JS object = two databases that must independently agree, with no arbiter.** This is workable at 20 days; it degrades as a function of total days and total distinct fields, not calendar time, and it's already showing cracks:

- **The Daily Log's EXAMPLE row was never deleted, and it's corrupting real averages.** `Read Me` (row 6) explicitly says "row 2 is a filled-in EXAMPLE — overwrite it with your real first day." It's still there: `Daily Log!A2 = 2026-08-14, weight 201.4, cal 1820, protein 178, fat 58, carb 138, fiber 32`. Real logging starts at row 3 (`2026-08-15`, weight 201). Because `Weekly Summary!B2:E2` (the week of 8/9–8/15) and `Daily Log`'s own `L`/`M` 7‑day-rolling-average columns both use `AVERAGEIFS` over `$A$2:$A$114`, that fabricated example row is included in week‑1 and early‑week averages, and it also inflates `Monthly Summary!F2` ("Days Logged" for August, via `COUNTIFS(...,"<>"))`. Nobody would notice from the Dashboard — it just quietly shifts the numbers. **Fix: delete/blank row 2, then re-check Weekly Summary row 2 and Monthly Summary row 2.**

- **The Dashboard's "Pace to goal (weeks, from today)" doesn't actually update from today.** `Targets!B19 = ROUND((B6-B7)/(B11/500),1)`, where `B6` is the fixed **starting** weight (201) and `B7` the goal (187) — this always evaluates to `14.0`, regardless of how much weight has actually been lost. The Dashboard tab labels this cell "Pace to goal (weeks, from today)," which it is not — it's "weeks from the original start, forever." The actually-useful number ("~11 weeks, early November," recalculated off the real 198 lb reading) exists only as text the coach typed into `PROFILE.md` by hand — the spreadsheet's own "auto-updates" promise (Read Me: "Everything else recalculates") is false for this cell.

- **Two governance tables have a hardcoded 30-row window that will silently stop working.** Both `Advisory Board Log`'s "Board Status" table (`D42:D54`, e.g. `=IF($D$39<10,...)` with `D39=COUNT($A$5:$A$34)`) and `Training & Recovery`'s "Field Status" table (`B42:D45`, e.g. `=IFERROR(_xlfn.MAXIFS($A$5:$A$34,...` and `MAX(Bloodwork!$A$5:$A$16)`) look up "last flagged / last logged" against a **fixed range of exactly 30 rows** (`$A$5:$A$34`). Real Advisory Board Log entries currently run through row ~24 (9/3). Once real rows extend past row 34, any newly logged day simply falls outside every `MAXIFS`/`COUNT` in that table — the 10-day "REVIEW — notify Roberto" rule (the system's whole safety net against a stale advisor or field going unnoticed) will stop firing, silently, with no error. This is the single most concrete "what breaks first as the log grows" answer: **it's not row count or file size, it's this specific hardcoded range**, and at current pace it has weeks, not months, of runway left.

- **Historical "on target" judgments use today's targets, not the targets that were live on that date.** `Targets!B12:B16` (calories/protein/carbs/fat/fiber) are single mutable cells that every historical Monthly Summary "days on target" calculation references. The targets were revised 8/22 (from Mifflin-St Jeor-derived numbers to the current manual ones); `Monthly Summary!G2` (August "days on target") will judge *all* of August — including days logged under the old target — against the current 1,850 kcal figure. History isn't actually preserved for "what was the target on that day."

- **The workbook has no cached formula results** (`data_only=True` returns `None` for every formula cell across every sheet), which means it was built/edited by a script rather than round-tripped through Excel/Sheets with a save. If this file is ever opened in a viewer that doesn't force a recalculation (a quick preview pane, some online viewers, certain automated pipelines), the Dashboard/Weekly/Monthly tabs will show blank instead of real numbers until something recalculates them.

**Is the constraint ("no backend, single file, no build step") worth challenging?** Not for the panel's *delivery* — a static Claude Artifact glanced at on a phone is the right form factor for this use case. What's worth challenging is treating "no build step" as license to hand-type the same numbers twice. The pragmatic fix keeps every stated constraint: have the coach generate the JS `DAYS` object, the weight-card numbers, and the chart's SVG coordinates *from* the xlsx (a small script/template pass run in the same turn) instead of retyping them from memory. That turns "keep two files in sync by hand" into "run one script off one source of truth," with zero added infrastructure.

## 2. Code quality — `webapp/pulso-panel.html`

- **The file isn't a complete, portable HTML document on its own.** It opens directly with `<title>…</title>` — no `<!doctype html>`, `<html>`, `<head>`, or `<meta charset/viewport>`. This works today only because the Claude Artifact publishing pipeline wraps published pages in a document skeleton. The copy of this file that lives in git (`webapp/pulso-panel.html`) is not actually self-contained outside that platform — opened directly (double-clicked, viewed via GitHub raw, hosted elsewhere) it has no declared viewport (bad mobile scaling) and no declared charset. Worth reconciling the "single self-contained HTML file" claim in the README with this dependency.

- **Only one section of the page is actually data-driven.** `renderDay()` + the `DAYS` object genuinely computes the five macro bars from data. Everything else — masthead date/ETA, the entire Bodyweight card (current/start/goal/%-to-go, including a manually-computed range-bar width), the whole 7‑Day Snapshot `<svg>` (hand-plotted `<path>`/`<circle>` coordinates), Today's Log, Debrief, Advisory Board, Recovery, and Bloodwork — is static markup that must be entirely rewritten by hand on every republish. It *looks* like a small app; it's ~90% a document regenerated from scratch each turn. That's the real "architecture" problem with this file, and it's the direct cause of the bug below.

- **Confirmed bug — self-contradicting Goal ETA.** On the "3 Sep 2026" edition of the panel, the masthead shows `Goal ETA: 28 Oct · 9.0 wk`. 3 Sep → 28 Oct is 55 days ≈ **7.9 weeks**, not 9.0 — the two numbers in the same UI element disagree with each other. This is exactly the kind of silent hand-arithmetic slip the whole hand-authored architecture is exposed to, and there is no step anywhere in the process that would catch it (this review caught it only by recomputing the date math independently).

- **Rounding/threshold inconsistency in `renderMacro()` (lines ~798–820).** For budget metrics (calories/carbs/fat), the color class (`good`/`watch`/`over`) is chosen from `Math.round(pct)` while the "N left/over" subtext is computed from the *unrounded* `value`/`target` difference — at the 89.5–90% and 99.5–100.5% boundaries these can visibly disagree (e.g. a value that rounds to exactly 100% renders amber ("watch") even though the raw subtext might say "0 left," not "0 over"). Separately: hitting the calorie target **exactly** (`pct === 100`) is classed `watch` (amber) — only strictly-under-90% ever reads as `good` (green) for a budget metric. That's a real product decision (landing exactly on-budget never shows "on track") currently buried in a `>=90` comparison rather than stated anywhere as intended behavior.

- **No structural link between a day's itemized log and its totals.** `items` is one pre-formatted HTML string per day; `cal/pro/carb/fat/fiber` are separately hand-typed numbers with no code path that sums the items to cross-check the day total. `itemCount` is a third, independently hand-maintained field used only for the "N items logged" caption. All three can drift from each other with no warning if a meal entry is edited later without re-totaling.

- **`innerHTML` used for author-authored content** (`document.getElementById('d-items').innerHTML = d.items`). No practical XSS risk today since only Claude writes this data, but there's no escaping layer anywhere in the pipeline — worth a flag if this content source ever changes (e.g. pasting raw OCR text with stray `<`/`&` into a note field).

- **Accessibility is inconsistent, not absent.** Positives: real `<button>` elements for the day pills (keyboard-operable, visible focus ring), native `<details>`/`<summary>`, `prefers-reduced-motion` respected, an `aria-label` on the SVG chart, and a full prose fallback (`week-summary`) alongside the chart. Gaps: the Advisory Board / vitals severity indicators reuse the identical glyph (▲, `&#9650;`) colored amber for "watch" vs. red for "critical" with no shape or text difference — a straightforward WCAG 1.4.1 (color-alone) failure for anyone who can't reliably distinguish amber from red. There's also no `aria-live` region around the macro block, so a screen-reader user tapping a day pill gets no announcement that the numbers below just changed.

- **Gap-day / partial-week chart logic is entirely manual.** The distinction between "Wed 9/2, a real gap" and "Fri/Sat, genuinely future" in the SVG is expressed by which specific `<circle>`/hatch elements were or weren't drawn that day, not by a rule the code enforces. Correct in this snapshot, but nothing stops a future day's chart from mis-hatching a day other than the author noticing by eye — same fragility as the ETA bug above, just not yet triggered.

## 3. Product / UX design

- The core hierarchy — weight first (framed correctly as "the motivator"), then today's intake, then the 7-day trend, everything else behind `<details>` — is well-reasoned and matches a "fast glance exec" goal. The 7-Day Snapshot (trend) + day-picker (point lookup) pairing genuinely serves two different jobs, as the docs argue; it isn't redundant.
- **Advisory Board's "Today" entry substantially duplicates the Debrief section directly above it** — on this snapshot, both sections restate the same "two egg-forward meals, protein at 39%, calories at 26%" observation in a second voice. For a stated "fast glance, no lecture" goal, this is the one place that currently reads as padding on a routine day; it earns its place better on days with a genuine flag to carry (as in the "Last Week" rows here) than as a daily fixture.
- **Adherence isn't surfaced anywhere on the panel**, even though the xlsx's own Dashboard tab already computes "Days Logged" and "Days On Target (±100 kcal)" per month. For a numbers-first exec, a single "18/20 days logged, on-target 12 days" stat would likely land better day-to-day than the Advisory Board narrative, and it's already computed — it just isn't piped to the artifact.
- **Estimate uncertainty is thrown away between chat and dashboard.** `CLAUDE_PROJECT_INSTRUCTIONS.md` explicitly asks for ranges when uncertain in-chat ("~550–650 kcal"), but every number that reaches the panel is a single point value with no residual range or confidence marker.
- Minor: the same "→" tip glyph is used with identical visual weight for a nutrition micro-correction (Debrief `.fix`) and a "raise this with your doctor" flag (Advisory Board / Bloodwork `.panel-tip`) — two very different stakes rendered as if equally weighted.

## 4. Process / workflow risk

**The actual failure mode, already demonstrated:** in roughly three weeks of light use this workflow has already produced at least three unnoticed inconsistencies — the never-deleted EXAMPLE row polluting week-1 averages, the self-contradicting Goal-ETA figure sitting on the published panel, and the 30-row governance-table ceiling that's about to be hit. None of these threw an error. They just quietly produce (or will produce) a wrong number, or silently stop enforcing the "notify me" rule that PROFILE.md and CLAUDE_PROJECT_INSTRUCTIONS.md both describe as the system's core defense against staleness. **That's the risk: not a crash, but a confidently wrong dashboard with no signal anything is off** — for a system feeding decisions off things like an ApoB flag, that's the worst-shaped failure mode available.

There is no validation step anywhere: nothing checks that `DAYS[today].cal` in the HTML equals the sum of that day's logged items; nothing checks that today's `Daily Log` row matches today's HTML entry; nothing checks that the JS `DAY_TARGETS` still matches `Targets!B12:B16`. The only "QA" is the same model, in the same turn, generating both files from the same short-term context — precisely the setup that let the ETA arithmetic slip through unchecked.

**Mitigations, cheapest first:**
1. Add a one-line self-check to the update habit itself: before republishing, have the assistant restate the arithmetic it's about to display (e.g. "3,497 = 1,685+550+775+487 ✓; ETA: 3 Sep + 63 days = 5 Nov, not 28 Oct — recheck"). Trivial, and would have caught the ETA bug immediately.
2. Stop hand-authoring the panel's data. Generate the `DAYS` object, weight-card numbers, and chart coordinates from the xlsx via a short script/template pass, so syncing the two files becomes "run a script" instead of "retype nine numbers from memory into a second format."
3. Fix the two hardcoded `$A$5:$A$34` ranges before they silently stop firing (a five-minute edit — extend the range or switch to whole-column references).
4. Delete the Daily Log's leftover EXAMPLE row now, and re-audit `Weekly Summary` row 2 and `Monthly Summary` row 2 (August) once it's gone.
5. Turn `Targets!B12:B16` into a small dated history table (target + effective date) instead of single mutable cells, so historical "on target" judgments use the target that was actually live that day.

## 5. Coaching methodology

- **Protein/fiber-as-floors, calories/carbs/fat-as-budgets** is a sound, well-established framing for this style of coaching, and it's implemented consistently in code (the `kind` parameter in `renderMacro`) — no notes here.
- **Advisory Board is the biggest concern in the whole project.** Real, named, identifiable public figures (Peter Attia, Andrew Huberman, etc.) are given synthetic, first-person-flavored commentary that both docs and the panel itself label "simulated" — but that disclaimer lives in one place: small italic text inside a `<details>` element that's collapsed by default. The always-visible summary line for that section just says "6 advisors · 2 open flags," with no "simulated" language at all. If this panel is ever glanced at by someone else, screenshotted, or simply recalled six months from now with the caveat forgotten, "Peter Attia flagged your blood pressure" reads as though the real Peter Attia reviewed the data — that's a real misattribution risk involving actual non-consenting people, not just a UX nitpick. **Recommendation:** put "(simulated)" in the always-visible summary itself (e.g. "6 advisors (simulated) · 2 open flags"), and consider whether real names are necessary at all versus persona labels ("Metabolic-health advisor, styled after Attia's public work") — especially before this is ever shared outside the owner's own eyes.
- **The 10-day silence rule is good governance in principle** — stale fields/advisors get flagged for a human decision rather than silently dropped or silently kept — but it's currently built on the hardcoded 30-row spreadsheet range described in §1, which undercuts the "trustworthy automation" story the docs tell about it. Fix the range before leaning further on this rule.
- **Bloodwork handling is the one area with no notes** — appropriately cautious framing ("not medical advice," named physician, no diagnosis language, explicit reference ranges).
- **The open ApoB/glucose flag has no persistent visibility outside the collapsed Bloodwork detail.** Given this is the single highest-stakes item in the system (a cardiovascular risk marker, explicitly flagged High), it currently has the same visual weight as "SpO2: 98%, no flag" one row below it, and nothing on the always-visible summary reminds the owner it's still an open item until the next panel is drawn. Worth more prominence than a line inside a collapsed section.
- Minor: the "brief, no lecture" tone promise is somewhat undercut by the combined length of Debrief + Advisory Board on an ordinary day (see §3) — worth periodically re-checking against the stated goal as habit (and the temptation to narrate more) grows with the log.

---

## If you only do three things

1. **Fix the two hardcoded `$A$5:$A$34` ranges** in `Advisory Board Log`'s "Board Status" and `Training & Recovery`'s "Field Status" before they silently stop enforcing the 10-day rule — the most concrete, time-bomb bug found, and closest to actually firing.
2. **Stop hand-authoring the panel's data.** Generate the `DAYS` object, weight card, and chart coordinates from the xlsx programmatically instead of retyping them from memory each turn — this is the root cause behind both the self-contradicting Goal-ETA figure and the leftover EXAMPLE row polluting week-1 averages.
3. **Move the Advisory Board's "simulated" disclaimer into the always-visible summary line** (or replace real names with styled personas) — right now, a glance at the collapsed dashboard presents AI inference wearing named real people's identities as if it were their actual opinion.
